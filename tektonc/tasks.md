### Task: `install-llmdbenchmark`

**Description:**

Install `llm-d-benchmark` into a Python venv on the shared `source` workspace so that `llmdbenchmark-standup` and `llmdbenchmark-teardown` tasks can activate it without re-installing on every pipeline run.

On first run creates the venv at `$(workspaces.source.path)/llmdbenchmark/.venv` and writes a sentinel file `.venv/installed-commit` containing the installed commit SHA. On subsequent runs compares `git_commit` against the sentinel: exits immediately (no-op) if they match, force-reinstalls if they differ.

**Inputs**:

- *git_commit* (required) — Git commit SHA to install; written to sentinel file after install

**Workspaces**:

- *source* — shared PVC where the venv is persisted across tasks

**Image**: `python:3.12.9-slim-bookworm` — `git` installed via `apt-get` within the script

**Install**: `pip install -e llm-d-benchmark/` (editable install from the submodule clone on the workspace)

## Stack Creation

Tasks to create elements of the model stack -- gateway, GAIE, and model servers.

To delpoy each stack, a unique DNS compatible identifier (`model_label`) is required. It serves two purposes:

(a) For each model service, a GAIE deployment is created. The  `InferencePool` identifies the pods of the model service using a set of match labels. Typically, the `llm-d.ai/model` label is used for this. Its value must be unique across all model services in the namespace. The `model_label` can be used for this.

(b) At the level of the Gateway, there must be a means to distinguish requests for one model service vs. another. For most workload generators, the simplest mechanism is to modify the request path by inserting a model specific prefix in the path. This prefix must be unique to the instance of the deployed model. Again, the `model_label` can be used for this (in an `HTTPRoute`).

### Task: `llmdbenchmark-standup`

**Description**:

Stand up a complete llm-d stack (gateway, GAIE, model service, HTTPRoute) using `llmdbenchmark standup`. Replaces the six sequential tasks (`deploy-gateway`, `deploy-gaie`, `deploy-model`, `pause-after-model-deploy`, `deploy-httproute`, `deploy-inference-objectives`). After standup, discovers the gateway endpoint via `llmdbenchmark run --list-endpoints` and emits it as a task result.

Three steps:

1. **write-config** — writes `spec_content` to `$(workspaces.source.path)/llmdbenchmark/spec.yaml.j2` and, if provided, `scenario_content` to `$(workspaces.source.path)/llmdbenchmark/scenario.yaml`. The spec content is a Jinja2 template generated by `prepare.py` with absolute paths already embedded for `values_file`, `template_dir`, and `scenario_file` — no `--base-dir` flag is needed.

2. **install-toolchain** — runs `llm-d-benchmark/install.sh --no-uv` to install the system toolchain (`kubectl`, `helm`, `helmfile`, `kustomize`, `jq`, `yq`) required by `llmdbenchmark standup`.

3. **standup** — activates the venv at `$(workspaces.source.path)/llmdbenchmark/.venv` (created by `install-llmdbenchmark`), verifies `llmdbenchmark --version`, then runs:

```
llmdbenchmark --spec <absolute-path-to-spec.yaml.j2> [--non-admin] standup \
  -p <namespace> \
  [--skip-smoketest] \
  [<extra_args>]
```

Then runs `llmdbenchmark --spec <spec-file> run --list-endpoints -p <namespace>` to extract the gateway endpoint URL and write it to the `endpoint` task result.

The pipeline runs in-cluster under a service account with RBAC configured by `setup.py`. No `--kubeconfig` flag is passed; llmdbenchmark uses in-cluster auth automatically.

`--non-admin` defaults to `"true"` because Tekton pods typically do not have cluster-admin. Set to `"false"` when the service account has cluster-admin privileges and cluster-level CRD/SCC installation is required.

**Parameters**:

| Param | Default | Description |
|-------|---------|-------------|
| `spec_content` | (required) | Content of the spec Jinja2 template; `prepare.py` embeds absolute paths for `values_file`, `template_dir`, and `scenario_file` |
| `scenario_content` | `""` | Content of the scenario YAML override; written to `/tmp/llmdbench-config/scenario.yaml`, which must match the `scenario_file` path in `spec_content` |
| `namespace` | (required) | Kubernetes namespace |
| `non_admin` | `"true"` | Pass `--non-admin` to skip cluster-admin operations |
| `skip_smoketest` | `"false"` | Skip post-standup smoketest |
| `extra_args` | `""` | Additional flags passed verbatim to `standup` |

**Workspaces**:

- *source* — provides the installed llmdbenchmark venv, llm-d-benchmark source, and written spec/scenario files

**Results**:

- *endpoint* — gateway endpoint URL extracted via `llmdbenchmark run --list-endpoints`

**Image**: `python:3.12-slim` across all three steps.
